## 三、LLM 真实调用证据（脱敏）

`evaluation/llm_smoke_test.py` 真实调用并生成 `evaluation/results/llm_smoke_test.json`，
记录 provider 主机、model、response_id、token 用量、提供的表、生成 SQL、校验与
执行结果、耗时（不记录 Key）。

- “哪个国家客户最多？”：规则兜底 `fallback_generate` 返回 **null**（规则字典无此问句），
  仍由真实 LLM 调用（含 response_id、token 用量）生成
  `SELECT Country FROM Customer GROUP BY Country ORDER BY COUNT(*) DESC LIMIT 1`，结果 USA；
- “消费总额最高的前 3 客户”：规则兜底 null，LLM 正确 JOIN Customer-Invoice，
  返回 Helena Holý（49.62）、Richard Cunningham、Luis Rojas。

这证明结果来自 LLM 而非规则。

## 四、确定性答案与查询解释

`nl2sql/explainer.py` 不二次调用大模型，避免二次幻觉与额外延迟：

- `build_answer`：用模板把结果转成一句中文答案，如“美国共有 13 客户。”；
- `build_query_logic`：从 SQL AST 提取表 / JOIN / 聚合 / WHERE / GROUP BY /
  ORDER BY / LIMIT，生成查询解释。

`agent/main.py` 的展示顺序为：答案 → 查询解释 → 生成 SQL → 查询结果 →
数据来源表 → 推理链。

## 五、JOIN 语义校验（中级：高质量多表关联）

`nl2sql/join_validator.py` 以直接表为节点、ON / WHERE 中经真实外键验证的等值
条件为边，要求多表经外键连通，拦截：

- `SELECT * FROM Customer, Invoice;`（逗号笛卡尔积）；
- `SELECT * FROM Customer JOIN Invoice ON Customer.City = Invoice.InvoiceDate;`
  （字段存在但并非外键的错误关联）。

校验失败把原因回喂 LLM 修正。

## 六、自我修正机制（故障注入验证）

机制：SQL 安全 / 表字段 / JOIN 校验失败时，把报错回喂模型重新生成，最多 3 次。
`tests/test_self_correction.py` 用 monkeypatch 注入故障（不依赖真实模型输出错误）：
第一次返回会被拦截的 SQL，第二次返回正确 SQL，断言最终成功、`attempts=2`、
trace 含“JOIN 校验未通过，回喂修正”。

> 标准 11 题均首轮成功，**自我修正触发次数为 0 / 11（有效修正样本 0）**；
> 机制本身已通过故障注入测试证明有效。

## 七、泛化实验（证明不依赖模型记住 Chinook）

`evaluation/synth/gen_synth_db.py` 生成表名 / 字段名完全陌生（t_a..t_f / f_xxx）、
外键拓扑为电商订单的合成库 + 中文别名层：

- 离线 8 项：合成图上 BFS 求出 `t_a→t_b`、`t_d→t_c`、多跳 `t_a→t_b→t_c→t_d`；
- 端到端（`synth_nl2sql.py`，结果 `generalization_results.json`）：4 个代表性问题
  全部一次成功，证明系统在模型未见过的库上照常工作。

## 八、多规模性能测试

`evaluation/perf_eval.py` 在 scale = 1 / 10 / 40（明细约 1 千 / 1 万 / 4 万）
分阶段计时，SQL 只生成一次并在各规模复用：

| 阶段 / 查询 | scale 1 | scale 10 | scale 40 |
| --- | --- | --- | --- |
| LLM 生成（与规模无关） | 0.52–0.61 s | 同左 | 同左 |
| Schema Linking + BFS | 0.001 ms | 0.001 ms | 0.001 ms |
| 执行：会员计数 | 0.25 ms | 0.29 ms | 0.26 ms |
| 执行：订单金额 JOIN 聚合 | 0.45 ms | 1.59 ms | 6.74 ms |
| 执行：明细销量（重） | 0.56 ms | 3.71 ms | 16.59 ms |
| 库文件大小 | 64 KB | 380 KB | 1440 KB |

复杂度：BFS O(V+E)、规则 Schema Linking 近常数；LLM 取决于 schema token、
主要是网络往返，与数据行数无关；SQL 聚合 / JOIN 近似 O(N)，主键计数近常数；
空间 O(N)。**瓶颈为 LLM 网络往返（约 0.5–0.6 s，占 95%+）**。优化方向：
prompt 缓存、连接复用、裁剪无关表、流式返回、外键 / 过滤列建索引、高频结果缓存。
